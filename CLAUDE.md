# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository status

This is a **dotfiles repository** in its initial state. As of this writing it contains only `README.md`, `LICENSE`, and a `.gitignore`. There is no source code, build system, test suite, or tooling configuration committed yet.

Per `README.md`, the repo is intended to hold **configs, scripts, and tools** — i.e. personal environment configuration and helper scripts, not a deployable application.

## Conventions to expect

- The `.gitignore` is the standard GitHub Python template (covers `__pycache__/`, virtualenvs, `.ruff_cache/`, `.pytest_cache/`, `.mypy_cache/`, build artifacts, etc.). This signals the toolchain to use when adding scripts here: **Python**, with `ruff`, `pytest`, and `mypy` as the implied lint/test/type tools.
- There are no Cursor rules, Copilot instructions, or other agent config files in the repo.

## Working in this repo

Because the repo is essentially empty, there are no project-specific build/lint/test commands to document yet. When the user adds content:

- If they add Python scripts, prefer `ruff` for linting/formatting, `pytest` for tests, and `mypy` for type checking (consistent with the `.gitignore`).
- For a dotfiles repo, files often need to be **symlinked into `$HOME`** (e.g. `ln -s "$PWD/<file>" ~/.<file>`) rather than copied. Confirm the user's preferred install/link mechanism before scripting it, and update this file once that mechanism exists.

## Scripts

The repo is published via **GitHub Pages** (`.nojekyll` at root; Settings → Pages → deploy from `main` / root), so scripts have a short canonical remote-invocation URL: `https://ohjho.github.io/dotfiles/scripts/<name>.py` (e.g. `uv run https://ohjho.github.io/dotfiles/scripts/convert_media.py --help`). The longer `raw.githubusercontent.com/ohjho/dotfiles/main/scripts/<name>.py` URL also still works.

- **`scripts/convert_media.py`** — Audio/video format converter built on `ffmpeg-python` (requires `ffmpeg` on `PATH`). Uses `typer` for the CLI and `loguru` for logging, with PEP 723 inline deps so it runs self-contained: `uv run scripts/convert_media.py INPUT --to FORMAT`. Accepts a single file, a directory, or a glob; `--output` is treated as a directory when it has no extension and a target file otherwise. Flags: `--to/-t` (required), `--output/-o`, `--recursive/-r`, `--audio-bitrate`, `--video-codec`, `--audio-codec`, `--dry-run/-n`, `--overwrite/-f`, `--verbose/-v`. Exit codes: `0` ok, `1` if any file failed, `2` if no inputs matched. Pure helpers (`normalize_format`, `build_output_path`, `build_output_kwargs`) carry doctests; per-file ffmpeg work is isolated in `convert_one` so `convert` is testable via an injected `convert_fn`.
  - Tests: `uv run --with ffmpeg-python --with typer --with loguru --with pytest pytest scripts/ --doctest-modules` (covers unit tests + doctests, no real ffmpeg needed).
- **`scripts/probe_media.py`** — Shows key information about a single video/audio file using `ffmpeg.probe` (a wrapper around `ffprobe`; requires `ffmpeg` on `PATH`). A friendlier replacement for `ffprobe -show_format -show_streams ... | grep`. Same stack as `convert_media.py` (`ffmpeg-python`/`typer`/`loguru`, PEP 723 inline deps): `uv run scripts/probe_media.py INPUT`. Accepts a **local path or a remote URL** (`http(s)`, `ftp`, `rtmp`, `rtsp`, ...; the existence check is skipped for URLs). Prints a readable summary (container, duration, bitrate/size, one labeled block per stream with codec/resolution/fps or sample-rate/channels) by default; `--json/-j` emits the full raw ffprobe JSON; `--verbose/-v` for debug logging. Two tiered integrity checks: `--check/-c` is a fast, remote-cheap **structural** check derived from the metadata already fetched (flags missing streams, zero/missing duration, video streams without dimensions) — it cannot see frame-level corruption; `--deep-check` runs a full decode pass (`ffmpeg -v error -i INPUT -f null -`) that catches bitstream corruption but is slow and downloads remote inputs in full (it supersedes `--check` when both are given). Exit codes: `0` ok, `1` probe failed or a check found problems, `2` file not found. Pure helpers (`is_remote_input`, `find_structural_issues`, `parse_decode_errors`, `format_frame_rate`, `format_duration`, `extract_stream_info`, `build_summary`) carry doctests; the side-effecting `ffmpeg` calls are isolated in `probe_file`/`run_integrity_check` so the formatting/parsing stays testable.
  - Tests: same invocation as `convert_media.py` above (`pytest scripts/ --doctest-modules`).
- **`scripts/list_s3.py`** — Lists S3 objects filtered by file suffix and prints them as keys, HTTPS URLs, or `s3://` URIs — a paginated, region-aware replacement for the `aws s3api list-objects-v2 ... --query "Contents[?ends_with(Key,'.mp4')...]" | sed 's#^#https://...#'` one-liner. Built on `boto3` with `typer`/`loguru` and PEP 723 inline deps: `uv run scripts/list_s3.py LOCATION`. `LOCATION` is either an `s3://bucket/prefix` URI or a bare bucket name; credentials/region resolve through boto3's normal chain (env vars, `~/.aws/config`, profiles). Unlike the bash one-liner it **paginates past the first 1000 keys** (via `get_paginator("list_objects_v2")`) and auto-detects the bucket region for URLs. Suffix filtering is client-side (S3 has no server-side suffix filter), case-insensitive, and accepts repeated or comma-separated values (`-s .mp4 -s mov` or `-s mp4,mov`); omit it to list everything. Flags: `--prefix/-p` (overrides any prefix in LOCATION), `--suffix/-s`, `--format/-f` (`key` default, `url`, `uri`), `--limit/-n`, `--region` (else auto-detected, only for `url`), `--profile`, `--verbose/-v`. Output is newline-separated on stdout (pipe-friendly); the count goes to stderr. URLs use virtual-hosted-style, falling back to path-style for dotted bucket names (TLS wildcard-cert mismatch). Exit codes: `0` ok, `1` AWS/boto3 error, `2` no bucket in LOCATION. Pure helpers (`parse_location`, `normalize_suffix`, `normalize_suffixes`, `matches_suffix`, `normalize_region`, `build_object_url`, `render`) carry doctests; the boto3-free `iter_objects` generator takes an injected page source, with the only AWS calls isolated in `s3_pages`/`resolve_region` so listing/formatting stays testable.
  - Tests: `uv run --with boto3 --with typer --with loguru --with pytest pytest scripts/list_s3.py --doctest-modules` (doctests only, no live S3 needed).
- **`scripts/upload_imgbb.py`** — Uploads a single local image to [imgbb](https://api.imgbb.com) and prints its hosted URL — a one-command replacement for the manual `curl` dance (read the file, base64-encode it, `POST` it with the key). Built on `requests` with `typer`/`loguru` and PEP 723 inline deps: `uv run scripts/upload_imgbb.py IMAGE`. The image is base64-encoded and sent via `POST` to `https://api.imgbb.com/1/upload` (key as a query param, image as form data); on success the direct image URL (`data.url`) is printed to stdout. The API key is an **optional** flag (`--api-key/-k`) that defaults to the `IMGBB_API_KEY` env var. Flags: `--api-key/-k`, `--name` (stored filename; defaults to the image's stem), `--expiration` (auto-delete after N seconds, 60–15552000), `--json/-j` (emit imgbb's full raw response instead of just the URL), `--verbose/-v`. Output is the URL on stdout (pipe-friendly); the status line goes to stderr. Exit codes: `0` ok, `1` upload failed (network error, non-2xx, or `success: false`), `2` usage error (file not found, or no API key supplied/in env). Pure helpers (`to_base64`, `build_payload`, `extract_url`) carry doctests; the side-effecting `requests.post` is isolated in `upload_image` (which returns the full parsed JSON payload) and the file read in `read_image`, so the encoding/formatting stays testable.
  - Tests: `uv run --with requests --with typer --with loguru --with pytest pytest scripts/upload_imgbb.py --doctest-modules` (doctests only, no live imgbb/network needed).
- **`scripts/screen_sessions.py`** — Recreates, inspects, snapshots, or stops the user's GNU `screen` sessions from the declarative manifest **`configs/screens.yaml`** (YAML: `sessions[].name`, `sessions[].windows[].{cwd, command}`, windows numbered by list order, no titles; `defaults.settle`). A one-command replacement for rebuilding every `screen -dmS` / `screen -X` session by hand after a reboot. Built on `pyyaml` + `psutil` with `typer`/`loguru` and PEP 723 inline deps: `uv run scripts/screen_sessions.py <subcommand>`. Subcommands: `launch` (creates each manifest session that is not running; a session that already exists is **skipped wholesale**, so it is idempotent), `status` (manifest vs. live: `[running]`/`[missing]`/`[dead]` per session, `#N OK`/`#N MISSING` per window, `EXTRA` for unmanaged windows, `[unmanaged]` for live sessions not in the manifest), `snapshot` (dumps every live session/window as manifest YAML to stdout or `-o FILE`; needs no manifest), `stop` (`screen -S PID.NAME -X quit` after a confirmation that flags the `$STY` session you are in). Manifest resolution: `--manifest/-m` → `./configs/screens.yaml` → `https://ohjho.github.io/dotfiles/configs/screens.yaml`. Shared flags: `--only/-s NAME` (repeatable), `--verbose/-v`; `launch`/`stop` take `--dry-run/-n`; `launch` takes `--settle SECONDS`; `stop` takes `--yes/-y`. Exit codes: `0` ok, `1` a session/window failed or `status` found something missing, `2` usage error (bad manifest, unknown `--only`, manifest unreachable). Design constraints (verified on macOS): `/usr/bin/screen` is **4.00.03 (2006) with no `-Q`**, so windows are discovered by walking the process tree `SCREEN → login → zsh → command` with `psutil` (`login` is setuid, so cwd/cmdline come from the `zsh` child; use `cmdline()` never `name()`); `screen -ls` exits non-zero on success so only stdout is parsed; `screen -S NAME` and `-p TITLE` prefix-match, so sessions are addressed as `PID.NAME` and windows by index; commands are typed into an interactive login zsh via `-X stuff` (full user PATH, drops back to a prompt on exit) and arrive **verbatim** — screen applies no `$`/`^`/`\` escaping to `-X` arguments. Launch sequence per session: `screen -dmS NAME` (run with `cwd=` of window 0) → `-p 0 -X stuff 'CMD\n'` → per extra window `-X chdir DIR`, `-X screen`, `-p i -X stuff` → bare `-X chdir` to reset. Pure helpers (`parse_screen_ls`, `find_live`, `expand_path`, `contract_home`, `parse_manifest`, `select_sessions`, `resolve_manifest_source`, `normalize_command`, `plan_create`, `plan_windows`, `plan_stop`, `match_windows`, `windows_to_manifest`, `render_status`) carry doctests; the side effects are isolated in `run_screen`, `execute` (takes an injectable runner), `list_sessions`, `walk_session`, `load_manifest_text`.
  - Tests: `uv run --with pyyaml --with psutil --with typer --with loguru --with pytest pytest scripts/screen_sessions.py --doctest-modules` (doctests only; nothing touches live screen sessions). Manual end-to-end check: `launch -m <throwaway manifest>` with a `test-` prefixed session, `status -m`, `screen -S PID.NAME -p 0 -X hardcopy out.txt` to see the typed command, then `stop -m ... --yes`.

- **`scripts/design_tokens.py`** — Validates and renders a W3C DTCG `design.tokens.json` written by the `design-derivation` skill (`.claude/skills/design-derivation/SKILL.md`), so consumer skills never hand-translate hex values. Built on `typer`/`loguru` + `tomlkit` (for the Streamlit config merge; colour/contrast math is stdlib `colorsys`), PEP 723 inline deps: `uv run scripts/design_tokens.py <subcommand>`, or remotely `uv run https://ohjho.github.io/dotfiles/scripts/design_tokens.py …` from any host project. Token file shape: colours in two sets `color.light` / `color.dark` with identical names, everything else shared; provenance in `$extensions["design-derivation"]["from"]`; font tokens may carry `$extensions["design-derivation"]["faces"]` = `[{url, weight?, style?, unicodeRange?}]` (font files for Streamlit's `[[theme.fontFaces]]`; malformed entries are warnings). **Core roles** every consumer may assume: `bg surface ink muted line accent accent-soft`, `font.display`/`font.body` (`font.mono` recommended), `radius.md`, `space.base`, `measure.body`; extra colour tokens carry the keystone (`hot/cold`, `offline/runtime`). Subcommands: `check TOKENS` (missing core roles, light/dark parity, invalid hex, malformed dimensions, and **WCAG AA** contrast: `ink` on `bg`/`surface` ≥ 4.5, `muted`/`accent` on grounds ≥ 3.0 → errors; weak extras → warnings; `--allow-single-theme` downgrades a missing dark set) and `render css|md|scss TOKENS` (`css`: `:root` + `prefers-color-scheme: dark` block, `--artifact` adds the `data-theme` guards claude.ai artifacts need; `md`: token tables, `--into design.md` rewrites the block between `<!-- tokens:start -->`/`<!-- tokens:end -->`; `scss`: a Quarto theme with `scss:defaults` Bootstrap variables + every token as a custom property in `scss:rules`, one file per `--theme light|dark`; `streamlit`: `.streamlit/config.toml` `[theme]` tables — dual by default (`[theme]` base/fonts/`baseRadius`+`buttonRadius`, `[[theme.fontFaces]]` from `faces`, `[theme.light]`/`[theme.dark]` with `accent → primaryColor+linkColor`, `bg → backgroundColor`, `surface → secondaryBackgroundColor+codeBackgroundColor`, `ink → textColor`, `line → borderColor+dataframeBorderColor`, `muted` dropped, plus `[theme.<t>.sidebar]` with sidebar bg = `surface`), `--theme light|dark` for a flat single `[theme]`, `--no-sidebar` to skip sidebar tables, `--into .streamlit/config.toml` merges via `tomlkit` replacing only the `theme` table and keeping every other table/comment (creates the file; idempotent); `-o FILE` else stdout). Verified against Streamlit 1.64 (`streamlit config show` recognises every emitted option). `tint COLOR --on GROUND [--min 4.5] [--direction auto|lighter|darker]` prints the nearest lighter/darker same-hue variants reaching the contrast target (exit `1` if none). `scheme ACCENT [--bias 0.08] [--format table|json] [-o]` proposes all seven core colour roles for both themes around one user colour (neutrals hue-biased by `bias`, accent nudged only as far as AA 3.0 needs, `muted` nudged to ≥ 3.0), as a table or a paste-ready DTCG `color` group with provenance `constraint`. CSS names drop the `color.<theme>` prefix and join other paths with dashes (`--font-display`, `--radius-md`), with `space.base → --space` and `measure.body → --measure`. Exit codes: `0` ok, `1` check found errors / `tint` found no variant, `2` usage error (missing/invalid file or colour, unknown target/format, flag used with the wrong target). Pure helpers (`flatten`, `color_set`, `parse_hex`, `contrast_ratio`, `hex_to_hsl`, `hsl_to_hex`, `adjust_to_contrast`, `tint_candidates`, `build_scheme`, `render_scheme_table`, `find_issues`, `css_var_name`, `format_value`, `format_font_plain`, `render_css`, `render_md`, `render_scss`, `render_streamlit`, `merge_streamlit_config`, `splice_between_markers`) carry doctests; file IO is isolated in `load_tokens` and the four commands.
  - Tests: `uv run --with typer --with loguru --with tomlkit --with pytest pytest scripts/design_tokens.py --doctest-modules` (doctests only). Manual check: `render md --into` against `.claude/skills/design-derivation/assets/example.design.md` and `check` on its sibling `example.design.tokens.json` (expect 0 errors); `render streamlit` on it should reproduce `example.streamlit.config.toml`, and `--into` a scratch `.streamlit/config.toml` with a `[server]` table then `uv run --with streamlit streamlit config show` should list every theme value as set.

## Skills

Project skills live in `.claude/skills/<name>/SKILL.md`. Two of them share the design-token contract above:

- **`design-derivation`** — reasons from content / audience / goal / constraints to a visual direction in **two asks, three with a full system**: round 1 confirms the read and the deliverable in one `AskUserQuestion` (files: `design.md` + `design.tokens.json` / md only / JSON only; scope: standard set or full system; finish: brief only or build); round 2 shows the proposed colour scheme (role, light/dark hex, reason) and asks `Use this proposal` / `I have a brand colour` / `I have a favourite colour` / `Use an existing palette`, **every time** — a supplied colour gets its role asked (accent / background / extra / ink) and the palette is rebuilt with `design_tokens.py scheme` / `tint`, recorded in a `## Colour scheme` section of `design.md`; round 3 (full system only) shows the spacing and type scales, shadow, motion durations and breakpoints with concrete alternatives and records the outcome in `## System`. Writes the files **next to the thing being designed** (`surge_artifacts/<slug>/`, `.streamlit/` for a Streamlit app), validates them with `design_tokens.py check`, and hands off to `surge-artifacts`, `artifact-design`, `frontend-design`, `quarto-writeup`, Streamlit (`render streamlit --into .streamlit/config.toml`), `dataviz`, `theme-factory`, or the `design` canvas with the matching `render` command. `assets/example.design.md` + `assets/example.design.tokens.json` (+ `example.streamlit.config.toml` rendered from it) are the generic worked example.
- **`surge-artifacts`** — publishes standalone pages to surge.sh; its Process step looks for the design files in the slug dir first and runs `design-derivation` when they are missing, then renders the `:root` token block with `design_tokens.py render css`.
- **`quarto-site-setup`** — orchestrates a new Quarto site in the alhaka shape (prose `index.qmd`, `posts.qmd` listing over flat `posts/*.qmd`, `pages/`, derived light/dark theme, GoatCounter, GitHub Pages workflow) by chaining `design-derivation`, `goatcounter-tracking` and `quarto-gh-publish-action`; reads the project brief before interviewing, confirms every move or delete, and writes `site.scss` fresh from the tokens each run.

## Configs

`configs/` holds declarative config consumed by the scripts; like `scripts/` it is served via GitHub Pages (`https://ohjho.github.io/dotfiles/configs/<name>`), so a script run from its remote URL can also fall back to the remote config.

- **`configs/screens.yaml`** — the GNU screen layout used by `scripts/screen_sessions.py` and the `relaunch-screens` skill (`.claude/skills/relaunch-screens/SKILL.md`). Keep it curated: `snapshot` dumps every idle shell too, so review its output before writing it back over this file.

# Guidelines
- update CLAUDE.md for each new features
- keep code modular to ensure ease in future refactoring
- use python and typer and loguru when writing scripts and make sure that it can be `uv run`
- use Google-style docstring for new functions and add a doctest compatible unit test if possible
